Shipping without breaking things, and one system designed end to end

Every product in this sector reaches people through software on their phones: the Neu app, DigiLocker, QuickBooks, a voter app. Getting a change to crores of phones safely is its own craft. Four ideas cover it: how mobile releases work, feature flags (switches the team controls from its servers), staged roll-outs (giving a change to a few people first), and observability (seeing what the software is doing). It ends with a capstone: the design of IRCTC’s Tatkal booking at 10 am, where caching, queues, consistency, scaling and payments all meet in one system. One running picture helps with the first four: a busy restaurant adding a new dish to the menu.

A. Mobile releases: why shipping to phones is different

Everyday picture. A restaurant that changes a dish on its website can fix a typo in a minute. A restaurant that has printed 10,000 menus and handed them to customers can’t; the old menus stay in circulation until people throw them away.

How it works. A website lives on the company’s servers, so everyone gets the new version the moment it is shipped, and a bad change can be rolled back in minutes. A mobile app is a copy on every phone ({{REF:webmob}}). A new version is built and signed, sent to Apple’s App Store and Google Play for review (Apple’s review usually takes hours to a day or two), and then reaches phones over days and weeks as they update, some automatically and some only when the user taps “update”. Meanwhile the old versions keep running. Teams therefore ship on a release train: a new version every one or two weeks on a fixed day, whatever is ready gets on, and what isn’t waits for the next train. An urgent fix (a hotfix) jumps the queue with its own release.

Worked example. An app with 1 crore users ships version 5.2. After a week about 40% have it; after four weeks about 68%; after three months still only about 75% ({{REF:adopt}}). So 25 lakh people are running code three months old, on many phone models and operating-system versions. Every server change must keep working for all of them: if the server stops sending a field the old version expects, that version breaks for 25 lakh people.

Two tools for the tail. A minimum supported version is a number the server checks: if a phone’s app is older, it shows “please update to continue”. It is used sparingly, for security fixes or when an old version would break (a payments app changing how it talks to NPCI), because every forced update loses some users who don’t update. Server-driven screens go the other way: the app asks the server what to show, in what order, with what text, and draws blocks it already knows ({{REF:sdui}}). A shopping app can rearrange its home screen for a Diwali sale on every version at once. The limit: a new kind of block the old app doesn’t know still needs a release.

Where it breaks. Apple or Google can reject a release a day before a big launch. A bug in an old version can’t be fixed at all for users who never update. And the store rules themselves change: both stores require apps to support recent operating systems within set deadlines. PM decisions: what goes on this week’s train and what waits; when a bug justifies a hotfix; when to force an update and accept losing some users; which screens should be server-driven so that marketing doesn’t need an engineer for every change.

“Why can’t we just roll back the app?” Because the old version is already on crores of phones; you ship a fix or switch the feature off from the server. “Should we force everyone to update?” Only for security or when the old version would break; each forced update loses some users, so measure how many.

B. Feature flags: switches the team controls from its servers

Everyday picture. The restaurant adds a new biryani. The chef keeps a switch on the kitchen wall. If diners send it back, the switch goes off and waiters stop offering it; nobody reprints the menu.

How it works. A feature flag is an if-statement in the code whose answer comes from a server: “if new_checkout is on for this user, show the new checkout; otherwise the old one.” Both versions of the code are already inside the app. When the app starts, it asks a flag service which flags are on for this user, giving details such as the user’s ID, phone type, city and app version, and keeps the answer for a short time ({{REF:flagflow}}). The team can then turn a feature on for 5% of Android users in Pune, for staff only, or for everyone, from a web page, in seconds. There are four common kinds. Release flags hide unfinished work until it is ready. Experiment flags split users into groups for an A/B test. Operations flags, or kill switches, turn a feature off in an emergency. Permission flags give a feature to a plan or a group of customers (Enterprise Suite features for IES customers only).

Worked example. A payments app switches its new UPI checkout on for 20% of users at 10:04 am. Failures rise from the usual 1.2% to 3.8% of payments. The alert fires at 10:07; the PM and the on-call engineer flip the flag off at 10:08:30; within a minute, as phones check in again, failures fall back to 1.2% ({{REF:killchart}}). About 4.5 minutes at 20% of traffic went through the bad checkout. If the app handles 3,000 payments a minute, that is 3,000 × 20% × 4.5 × (3.8% − 1.2%) ≈ 70 extra failed payments, not the thousands a new app release would have taken hours to stop.

Where it breaks. Flags pile up. An old flag nobody removes becomes a trap: in August 2012 the US trading firm Knight Capital reused an old flag for new code, one of its eight servers still ran the old code the flag switched on, and it lost $440 million in 45 minutes. Too many flags also multiply the combinations nobody has tested (ten on-off flags make 1,024 versions of the app), and a flag service that goes down must fail safe, falling back to the old behaviour. PM decisions: which features ship behind a flag (anything touching money, sign-up or a big screen); who may flip it and how fast phones must notice; the rule that every flag has an owner and a removal date, so flag debt is cleared each quarter.

In the interview · Feature flags

“How would you launch a risky change to checkout?” Behind a flag, to staff first, then 1%, then wider, with payment success as the guardrail and a kill switch that works in under a minute. “What’s the risk of flags?” Old flags nobody removes; set an owner and a removal date for each.
