A/B testing basics: did the change cause the result?

PhonePe wants more people to pay bills on autopay, because an autopay user comes back every month without being reminded. A designer proposes a button on the success screen: “Autopay next month’s bill”. The team could ship it to everyone and watch the numbers. But October has Diwali, salary days and a new fee on merchants, so any rise or fall could come from anything. An A/B test fixes that: show the button to a random half, hide it from the other half, and compare.

Control / variant: the current experience (A) and the changed one (B).

Primary metric: the one number that decides the test, chosen before it starts (autopay set within 7 days).

Guardrail metric: a number that must not get worse (bill-payment success, complaints).

Statistically significant: a gap too large to be luck. By convention, a gap this big would appear by chance less than 5% of the time (p < 0.05).

Power: the chance the test spots a real effect of a given size; teams usually aim for 80%.

MDE (minimum detectable effect): the smallest gap worth detecting, which sets the sample size.

Light maths: how many users, how many days?

A handy rule of thumb for an 80%-power test at 5% significance: users needed in each group ≈ 16 × p × (1 − p) ÷ δ², where p is today’s rate and δ the gap you want to detect. With p = 2% and a hoped-for 2.2% (δ = 0.2 points = 0.002): 16 × 0.02 × 0.98 ÷ 0.002² = 16 × 0.0196 ÷ 0.000004 = 78,400 users per group. At 20,000 new users per group per day, that is 4 days. Halve the gap you want to see and you need four times the users, because δ is squared.

When it breaks
  • Peeking: checking daily and stopping on the first good day turns luck into “wins”. Fix the duration in advance.
  • Too many metrics: test 20 metrics at 5% and about one will look significant by chance. Pick one primary metric.
  • Users who affect each other: in P2P payments a variant user pays a control user, so the groups leak. Split by city or friend groups instead.
  • Novelty: a shiny new button gets clicked for a week, then ignored. Run long enough to see it fade.
Key idea · The PM decisions this drives
  • The hypothesis and the one primary metric.
  • The smallest effect worth shipping, which sets the size and length.
  • The guardrails that can veto a “win”.
  • What happens if the result is flat: stop, or try a bolder variant.
  • When not to test: legal fixes, or changes too small to measure.
In the interview

“How would you test this feature?” Answer in one breath: “My hypothesis is that the autopay button raises autopay sign-ups. Primary metric: autopay set within 7 days. Split bill payers 50:50 at random. I’d want to detect 2.0% to 2.2%, which needs about 78,000 users per group, so I’d run two full weeks across the bill cycle. Guardrails: bill-payment success and complaints. Ship if the primary metric wins and the guardrails hold.”
