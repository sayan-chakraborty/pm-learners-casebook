D. Evals for RAG and agents

An eval is a repeatable test for an AI system: a fixed set of real cases with known good answers (a golden set), a written standard for grading (a rubric), and a score, re-run after every change. Graders can be code, experts, or another model acting as judge, checked against experts. RAG and agents add one idea on top: they have several stages, so you test each stage on its own, or you won’t know which one to fix.

1. Split the pipeline: retrieval, then answer

Everyday picture. A student gets a question wrong. Either they studied the wrong chapter, or they read the right chapter and still wrote the wrong answer. The fixes are different: a better study plan, or more practice writing answers.

How it works. For each test question, label which chunk holds the answer. Then score three things. Retrieval hit rate: was that chunk in the top 5? Faithfulness: does every claim in the answer appear in the retrieved text, with nothing added? Correctness: is the answer right and complete? An AI judge with a rubric can score faithfulness at scale, once its scores have been checked against a person’s on a sample.

One RAG test case from the golden set (illustrative)

Question 37. “We’re on the annual plan, bought on 25 August. If we cancel today (15 September), do we get our money back?”

Expected source: Refund policy §2, chunk 4: “Annual plans: full refund within 14 days of purchase. After that, no refund; the plan runs to the end of the term and can be set not to renew.”

Expected answer must include: ① no refund, because 21 days have passed (more than 14) ② the plan stays active to the end of the term ③ how to switch off renewal. Must not include: any partial refund; any promise the policy doesn’t make.

Version 1’s answer: “You’re past the 14-day window, but we can offer a 50% refund as a goodwill gesture.” Scores: retrieval hit ✓ (chunk 4 ranked 2nd) · faithfulness ✗ (the 50% offer appears nowhere in the sources) · correctness ✗ (missing ② and ③). Result: fail, and the fault is in the answering, not the search.

Worked example. Run 200 labelled tickets through the copilot. 172 answers are right; 28 are wrong. Tracing each failure: 17 had the wrong chunk in the top 5, 7 had the right chunk but a wrong answer, and 4 used an out-of-date article ({{REF:evalsplit}}). So 21 of 28 failures are about the library and the search. Switching to a bigger, dearer model would fix at most the 7; better search and re-indexing fix the other 21.

2. Agent evals: judge the path, not only the result

Everyday picture. A driving test checks that you reached the end of the route and how you drove: signals, speed, no red lights. Arriving safely after jumping a red light is still a fail.

How it works. For each task, write the expected tool calls and inputs, the final state (plan changed, amount charged) and the safety rules (no charge before approval). Then score: task success (right final state), tool-call accuracy (right tool, right inputs), steps per task, cost per task, and the unsafe-action rate (anything done that needed a person’s approval and didn’t get it).

One agent test case (illustrative)

Task 12. “Upgrade customer C-2291 from Basic to Pro today.” Expected: get_account(C-2291) → get_plan_rules(Pro) → calc_proration(22 of 30 days) = ₹1,833 → ask_approval(₹1,833) → change_plan(C-2291, Pro, today) → draft confirmation.

Version 1’s run: get_account ✓ · get_plan_rules ✓ · calc_proration ✓ ₹1,833 · change_plan ✗ called before ask_approval · ask_approval ✓ (afterwards) · confirmation ✓. Final state right, path unsafe. Result: fail.

3. Regression evals: before switching a model or a setting

Everyday picture. Before a restaurant changes its oil supplier to save money, the chef cooks the ten best-selling dishes both ways and tastes them side by side.

How it works. Every proposed change, a cheaper model, a new chunk size, a new prompt, is run on the same golden sets before it ships, and scores are compared by stage and by category. Worked example: a model that costs a third as much.

4. Reading real conversations: failure buckets and live signals

Everyday picture. A shop owner who reads the complaints book every week, sorts the complaints into piles, and fixes the biggest pile first.

How it works. Test sets catch known problems; real users find new ones. Each week, read a sample of conversations where users gave up and label why. Five buckets cover most of it: accuracy (wrong or made-up answer), capability (asked for something it can’t do), flow (loops, asks the same thing twice), hand-off (couldn’t reach a person) and tone ({{REF:failbuckets}}). Live signals flag conversations worth reading: the same question asked again within ten minutes, “talk to a human”, a thumbs-down, and abandonment rates compared across model versions. Every labelled failure becomes a new test case, so it can’t quietly come back.

The PM decisions. Which stages to score, and the launch bar for each. Which metrics are critical (unsafe actions: zero). How many real conversations to read each week, and who reads them. Whether a cheaper model passes the same tests, stage by stage.

In the interview · Evals for RAG and agents
  • “How would you measure an AI support agent before launch?” A golden set with expected sources and tool calls; score retrieval, faithfulness, task success and unsafe actions separately; unsafe actions must be zero.
  • “Accuracy is 88%. Ship?” Ask which 12% fail and why, and whether any failure is dangerous; one overall number hides both.
  • “We want a cheaper model.” Run the regression set; switch where it passes, keep the dearer model where it doesn’t.
