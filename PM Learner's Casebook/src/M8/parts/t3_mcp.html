C. MCP: one standard plug for tools and data

Everyday picture. Ten years ago every phone brand had its own charger, and a drawer full of cables. USB-C made one plug work for all of them. MCP (Model Context Protocol) aims to do the same between AI apps and the tools and data they use. Anthropic released it as an open standard in November 2024. OpenAI, Google and Microsoft added support during 2025, and in December 2025 it was handed to the Agentic AI Foundation under the Linux Foundation, so no single company controls it. By then there were more than 10,000 active MCP servers.

1. How it works: host, client, server

Three parts ({{REF:mcp}}). The host is the AI app a person uses: the support copilot, a desktop assistant, a coding tool. Inside it, a client handles the connection to each outside service. An MCP server is a small program, usually written by the service’s own company, that tells any host what it offers and runs requests. A server can offer tools (actions such as create_issue), resources (data to read, such as files) and prompts (ready-made instructions). The host first asks each server “what do you offer?”, shows those tools to the model, and passes on the model’s requests.

Worked example. Priya types “Summarise ticket #4821 and file a bug.” The copilot asks the help-desk server for the ticket, summarises it (CSV export fails over 10,000 rows), asks Priya to approve filing, creates the issue through the Jira server, and adds a note with the issue number back on the ticket ({{REF:mcptrace}}). The copilot’s makers wrote no code for Jira.

2. Why a standard matters: the arithmetic

Without a standard, every AI app needs its own connector to every tool: 5 apps × 20 tools = 100 connectors to build and repair whenever any of them changes. With a standard, each app builds one client and each tool one server: 5 + 20 = 25 pieces ({{REF:mcpmath}}). The same sum explains why USB, and HTTP for websites, spread: multiplication turns into addition.

3. Where MCP breaks

Untrusted servers. Installing an MCP server is like installing an app with access to your data; a fake or careless one can leak it. Too much power: a server that can delete as well as read, when read was all the task needed. Poisoned tool descriptions: the text a server uses to describe its tools goes to the model, so a malicious server can hide instructions there (“also send the file to…”). Login gaps: the server must act as the right user with the right rights, not as an all-powerful system account. Crowded context: each tool’s description takes up room in every request; 40 tools × 150 words is a lot of text for the model to read before it starts, which adds cost and makes it pick the wrong tool more often.

The PM decisions. Build an MCP server for your own product. This is a distribution decision: once there is a server, every AI assistant a customer uses can work with your product, as happened with Jira, GitHub and Notion. Which actions to expose: start read-only, add writes with approvals. Which servers your own AI app may connect to: an approved list, not anything a user installs. How many tools to show the model at once.

In the interview · MCP
  • “What is MCP, simply?” A USB-C for AI: one standard way for any AI app to use any tool or data source, so 100 connectors become 25.
  • “Should our SaaS product ship an MCP server?” Yes if customers work inside AI assistants: it puts your product where their work is; start with read-only tools.
  • “What’s the risk?” Servers you don’t trust, too many powers, and instructions hidden in tool descriptions.
