Evals: how you know an AI feature is good enough

A normal feature can be tested with a checklist: tap “Cancel” and the order is cancelled. An AI feature can’t. Give the clinic assistant the same folder twice and the brief may be worded differently; give it a thousand folders and you can’t read every output. An eval (short for evaluation) is a repeatable test for an AI system: a set of inputs, a written idea of what a good output contains, a way to grade each output and a score. The eval set is where “good enough to ship” actually lives. The running example is one product: an assistant that turns a patient’s folder of reports into a one-page brief for the doctor.

1. Why a demo isn’t enough

Everyday picture. A new cook makes one excellent biryani for the owner’s tasting. That tells you little about the 200 plates on a Sunday, with different rice, a rushed kitchen and a customer who wants it less spicy.

How it works. A demo shows one input chosen by the builder. Real use brings blurry photos, handwritten prescriptions, two patients with the same surname and reports in Marathi. Quality has to be measured across many realistic cases, and measured the same way every time something changes. The team repeats a loop ({{REF:evalloop}}): collect real cases, write down what good looks like, change something, run every case, decide whether to release, and feed live mistakes back in as new cases.

2. The golden set: real cases with known answers

Everyday picture. A board exam has a marking scheme written before anyone sits the paper: “full marks if the answer mentions these three points”.

How it works. A golden set is a fixed collection of real inputs, each with an expert’s note of what a correct output must include and must not include. For the clinic assistant: 60 anonymised folders from pilot clinics (names and phone numbers removed), chosen to cover what actually walks in. A doctor writes the must-haves for each. Guidance from AI labs is that 20–50 cases drawn from real failures is already a strong start; the set grows from there.

One test case from the golden set (illustrative)

Folder 17. Woman, 58. Six items: HbA1c 7.8% (Nov 2025) and 8.9% (Mar 2026); creatinine 1.6 mg/dL (Jan 2026); a typed prescription for metformin 500 mg twice a day; a handwritten note “allergic to sulfa drugs”; an old 2015 X-ray report. Questionnaire (in Marathi): tired for two weeks, more thirst.

Must include: ① current medicine: metformin 500 mg twice daily ② sulfa allergy ③ HbA1c rising, 7.8 → 8.9 ④ creatinine 1.6 flagged as above range ⑤ symptoms: tiredness and thirst, two weeks.

Must not include: any diagnosis (“poorly controlled diabetes”, “kidney disease”); any advice on medicines; the 2015 X-ray presented as current.

Version 1’s brief: got ①, ②, ③ and ⑤; wrote creatinine as “16”, missing the decimal point; no diagnosis. Result: fail (a critical fact wrong).

3. The rubric: what “good” means, in points

Everyday picture. A cooking competition scores taste, presentation and time separately, so a beautiful dish served cold doesn’t win.

How it works. A rubric splits quality into criteria, each with a score and a written description of every level. Some criteria are critical: fail one and the whole output fails, whatever the other scores.

PM decision. Writing the rubric is the PM’s job with a domain expert, because it is the product spec. The launch rule might be: at least 95% overall pass, and zero critical failures on allergies and medicines.

4. Who grades: people, code or another AI

Everyday picture. In a big exam, a machine marks the multiple-choice sheets, teachers mark the essays, and a senior examiner re-marks a sample of the teachers’ work to check they agree.

How it works. Three kinds of grader, used together. Code checks handle what can be checked mechanically: is the brief under 120 words, does every number appear in the source text, are banned words like “diagnosis” absent? Fast and exact. Doctors grade against the rubric: the most trusted, but 60 folders × 3 minutes is three hours of a doctor’s time per run. An AI judge (a second model given the rubric and asked to grade) is cheap enough to run on every change, but it must first be checked against the doctors. Grade 100 briefs both ways ({{REF:agree}}): if they agree on 88, look hard at the 12 where they don’t. Here the judge passed nine briefs a doctor failed, all with misread decimals, so a code check for numbers was added.

PM decision. Use code checks wherever possible, the AI judge for everyday runs, and doctors for the monthly check and for every disagreement. Never trust an AI judge you haven’t compared with people.

5. Offline and online: before and after release

Everyday picture. A car is crash-tested in a lab before sale, and the company still tracks real accidents and recalls afterwards.

How it works. Offline evals run the golden set before release: fast, repeatable, and nobody is exposed to a bad version. Online evals watch real use after release ({{REF:offon}}): how often doctors edit a brief (8% here), how often they tap through to the source, minutes saved, and a weekly audit where a doctor checks 100 random live briefs for critical misses. When the team wants to compare two versions on real users, it runs an A/B test, read exactly like any other.

6. Regression evals: before any change ships

Everyday picture. A pharmacy switches to a cheaper supplier of the same tablet. Before switching, it checks each batch as well as the average, because one bad batch is one too many.

How it works. A regression is something that used to work and now doesn’t. Every change (a new model, a new prompt, a cheaper provider) is run on the whole golden set and compared category by category with the current version. Here, version 2 uses a model at half the price. Its overall score falls only 1.3 points, but handwritten prescriptions fall 13 points. The rule “no category may fall by more than 2 points” blocks the release.

PM decision. The options are a product call: keep v1, or use v2 for typed reports and v1 for handwriting (the cost saving shrinks but stays), or improve v2’s handwriting reading and re-run. Whichever you choose, the 12 handwriting cases stay in the set forever.

7. Red-team sets: trying to break it on purpose

Everyday picture. A bank hires people to try to break into its own branch before a real thief does.

How it works. A red-team set is a collection of inputs designed to make the system fail: tricks, edge cases and dangerous situations. Each has an expected safe behaviour.

Attack or edge caseExpected behaviourv1

PM decision. The two failures become fixes and permanent test cases before the pilot widens. A red-team set is never finished: every new way a real user surprises the system goes in.

In the interview · Evals
  • “How would you know the AI feature is ready to launch?” A golden set of real cases, a rubric with critical criteria written with an expert, a launch bar, and a red-team set that must pass.
  • “The new model is cheaper and scores almost the same. Switch?” Compare by category, not on average; one category falling 13 points can hide inside a 1-point average drop.
  • “Can we use an AI to grade the AI?” Yes, once you have checked it agrees with experts and added code checks for what it misses.
